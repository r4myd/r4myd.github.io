Portal Entry Runner

    
One spreadsheet in. Hundreds of cases walked through a web portal’s whole workflow.

  


  
    
    
  1. Open
  2. Rework
  3. Pick
  4. Pin on map
    5. 
    
  5. Upload
  6. Fill form
  7. Submit
  8. Send
    9. 
  


  

    

      
Every case on the portal had to be opened, sent back, picked up, pinned on the map, given its document, filled, submitted and finally sent to the client. By hand that is nine screens per case, a few hundred times over.

      
The runner reads the case list from Excel and does it the way a careful person would. Before every click it reads what the portal is actually showing, waits between requests, and if you press Stop or the connection drops, it carries on from the exact step where it paused.

      
    
        
  • Its requests match the browser’s own byte for byte, checked by golden tests.
    • 
        
  • 37 tests run against a mock portal, so the real one is never touched while testing.
    • 
        
  • A case with a missing value is held back with the reason shown. Nothing is guessed.
    • 
      

    

    

      
Built with
Python, requests, SQLite, a plain HTML/JS control panel

      
One full case
About 9 minutes, unattended

      
Safety
Paced 6–12 s between requests, retries with back-off, stops itself after 3 failures in a row

    

  

  






  

    
Agent workflows that don’t guess

    
How I run agents on big jobs: one written brief, parallel packets, self-checks, and a person signing off.

  


  

  

    

      
When a job is too big for one prompt, I don’t write a bigger prompt. I split the work into small packets, run agents on them in parallel, and give every agent the same written brief.

      
The brief is the real work: what done looks like, read-only access by default, no copying a value from one item to another, and a blank with a written reason whenever something can’t be proved. Every agent checks its own output before handing back, then plain code sweeps the merged result: ranges, totals and duplicate rows. A person signs off at the end.

    

    

      
Pattern
Brief → packets → parallel agents → self-checks → merge → human sign-off

      
Rules
Read-only by default, no guessing, every blank explained

    

  







  

    
Land rate from a map pin

    
Rajasthan’s government land rates, searchable offline and answered from a coordinate.

  

  

    

      
Every property valuation has to quote the government’s minimum land rate for its area. The official portal only searches by name, and people in the field come back with a coordinate.

      
I wrote a harvester that keeps a local copy of every rate for all 41 districts, with history and the boundary of each colony. A pin now returns its rate in milliseconds without internet, plus live land-use, zone and khasra from the state GIS, and makes the map images that go with it. It is the first tool in the valuation industry that gives an up-to-date DLC rate straight from a coordinate.

    

    

      
Built with
Python, SQLite, ArcGIS REST, Pillow

      
Data
63,775 current rates, history back to 2014

      
Manners
Paced, resumable downloads that never overload the government server

    

  

  

    
    
  







  

    
Portal auto-fill

    
A Chrome extension that types a finished Excel file into eight different lender portals.

  

  

    

      
Some portals want the same data typed in field by field: 60 to 380 fields a case. The extension reads the case’s Excel file and fills the form. It finds values by their labels rather than fixed cells, so a slightly different layout still works, and it flags a section in red instead of guessing. Saving and submitting stay a person’s click.

      
It began as five separate extensions. I merged them into one core with a small plug-in per portal after a review found the same bugs copied into all five.

    

    

      
Built with
JavaScript (Manifest V3), SheetJS, a Node test harness

      
Tested on
633 real past files for one portal: 3,798 of 3,798 option fields read right

    

  

  

    
    
  







  

    
A dashboard that talks in sentences

    
Three years of monthly exports turned into something the owner reads every morning.

  

  

    

      
36,000 case records sat in separate monthly spreadsheets. I loaded them into SQLite and built a dashboard on top: which clients are growing, which have gone quiet, how the month is tracking, which weekdays are busiest.

      
The alerts read like a colleague wrote them: “no cases from this client for 74 days, worth a call.”

    

    

      
Built with
Python, SQLite, Chart.js

      
Data
36,308 records, 2023–2026

    

  

  

    
    
    
  







  

    
Every bank auction in the state, on one map

    
Three auction sites scraped each morning, scored against the district median.

  

  

    

      
Auction notices are spread over three websites in three formats. This collects them daily, keeps Rajasthan only, pins each property and compares its reserve price per sq ft with the median for its district, so a cheap listing stands out.

    

    

      
Built with
Python, Flask, BeautifulSoup, Leaflet

      
Last run
1,266 properties across 47 districts
